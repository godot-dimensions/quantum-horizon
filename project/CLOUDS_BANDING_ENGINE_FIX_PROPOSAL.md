# Proposed engine-level fix: grazing-angle Cross-Section slicing instability

Standalone problem statement + proposed fix, for external review before implementation. Full
investigation history (everything ruled out, and why) is in `CLOUDS_BANDING_TECHNICAL_SUMMARY.md`
in the same repo, but this document doesn't depend on it.

**Update, before finalizing — corrected after a rigorous direct look (see below)**: an isolation
test was run to separate how much of the visual severity comes from the geometric singularity
itself versus a *separate*, previously-known bug in this project's own noise atlas (a hand-packed
grid of 48 tiles in one 2D image, whose mipmaps are generated by downsampling the whole packed
image uniformly — corrupting every mip level above 0 by blending unrelated neighboring tiles
across their shared boundaries; forcing LOD 0 everywhere was the existing workaround). Swapping in
a single, ordinary, properly-seamless, correctly-mipmapped 2D noise texture — sampled with normal
automatic LOD selection, no atlas indexing, no forced LOD 0 — at the same 88° rotation, with every
shader-side mitigation disabled: **the same underlying stripe pattern is still visible, confirming
the geometric singularity is real** — but an initial read of this result as "severity dramatically
reduced" **did not hold up** once checked properly. A same-rotation, same-crop, explicitly-labeled
side-by-side render (`_verify_screenshots/isolation_final_labeled_composite.png`, built and viewed
directly rather than judged from a full-frame glance) shows the two configurations are **nearly
indistinguishable** — same stripe positions, same sharp near-binary contrast, same overall
severity. **Proper texture filtering, on its own, does not meaningfully reduce this artifact.**
That makes sense in hindsight: the geometric singularity corrupts the *sampling coordinate itself*
(`local_pos`, confirmed via the checkerboard test above), so no amount of downstream filtering on
what gets sampled *at* that coordinate can fix a coordinate that's already wrong. The atlas's mip
corruption is still real, still worth fixing, but purely as **independent hygiene** (its own,
unrelated minification/anti-aliasing problem at ordinary viewing angles) — not as a companion fix
for this banding artifact. See the section below, retitled accordingly.

## The problem, precisely

This is a custom Godot 4 fork with a genuine 4th spatial dimension (`engine/modules/4d/`). 4D
objects are represented as sets of **tetrahedra** (4-point 3D simplices embedded in 4D space).
Every frame, the "Cross-Section" rendering pipeline slices each tetrahedron against the camera's
current 3D viewing hyperplane (`w=0` in the object's transformed space), producing 0, 1, or 2
output triangles per tetrahedron. This is the shared rendering path for every 4D object in the
project — terrain, props, and a cloud-layer object where the bug was first noticed.

The vertex-stage math (from `engine/modules/4d/render/cross_section/tetra_cross_section_shader.glsl`,
which every custom 4D material must reproduce verbatim since the engine only auto-assigns it
when a material's shader slot is null):

```glsl
int position_edge = CROSS_SECTION_LOOKUP[face + (vertex_id % 3)];
int edge_vert1 = TETRAHEDRON_EDGE_TO_VERTEX_MAP[position_edge * 2];
int edge_vert2 = TETRAHEDRON_EDGE_TO_VERTEX_MAP[(position_edge * 2) + 1];
vec4 position1 = verts[edge_vert1];   // view-space corner, w1 > 0
vec4 position2 = verts[edge_vert2];   // view-space corner, w2 < 0 (opposite sign - that's why this edge crosses)
float mix_weight = position1.w / (position1.w - position2.w);  // always in [0,1]
vec4 position = mix(position1, position2, mix_weight);          // the actual output vertex
```

`mix_weight` is mathematically exact and always bounded in `[0,1]` — but its **sensitivity** to
the exact values of `w1`/`w2` is `d(mix_weight)/dw1 = -w2/(w1-w2)^2`, which diverges as
`(w1-w2) → 0`. This happens specifically when a tetrahedron is only *just* starting to cross
`w=0` — nearly tangent to the camera's slicing hyperplane, a genuine "viewed edge-on" case (in
our project this happens at extreme combined 4D rotations, but it can happen for any 4D object
at the right viewing angle).

**What we've confirmed, precisely, through direct testing (not guesswork):**

1. **Not a floating-point precision bug.** We reformulated the denominator to avoid catastrophic
   cancellation (computing `(local_vert1 - local_vert2)` — a small, well-conditioned local-space
   difference — transformed once, instead of subtracting two independently-transformed,
   large-magnitude values). Rendered before/after at the exact problem angle: **zero visible
   difference.** This proves the instability is a property of the *exact* mathematical formula,
   not a numerical-precision artifact — `d(mix_weight)/dw` really does diverge, with perfect
   arithmetic, as `(w1-w2)→0`.

2. **It's the true geometry, not just a texture-sampling artifact.** There's an exact algebraic
   identity: `position = modelview_basis * local_pos + modelview_origin` holds regardless of
   `mix_weight`'s value (mixing commutes with any affine transform). We visualize a
   sampling-only coordinate (`local_pos`, interpolated the same way as `position` but from the
   raw untransformed corners) for texturing; by this identity, if `local_pos` is unstable near a
   grazing crossing, the *true rendered position* is equally unstable. Direct test: a fine
   checkerboard pattern built purely from `local_pos`, no texture involved at all, shows the
   exact same coherent-banding structure as the original texture artifact. **This means the bug
   affects the actual triangle positions Cross-Section produces near a grazing crossing, for any
   material** — a flat-shaded, untextured surface would show it too, just far less visibly than
   a high-frequency noise texture would.

3. **GPU derivatives (`dFdx`/`dFdy`/`fwidth`) cannot see it, because it's a between-primitive
   discontinuity, not a within-primitive gradient.** These instructions measure the rate of
   change of an interpolated value *within one triangle's own linear interpolation* — they have
   no visibility into a neighboring, independently-rasterized triangle from a different
   tetrahedron. Direct test: `fwidth()` on the affected coordinate reads flat and uniformly low
   across the entire severely-affected region. This isn't a bug in the derivative — it's
   correctly reporting that each individual triangle's own interior gradient is low; the actual
   large jump happens *between* triangles, which the instruction structurally cannot measure.

4. **Not sub-pixel geometric aliasing.** Since derivatives can't see it, the natural hypothesis
   was many tiny, differently-shaded triangles inside one pixel — the textbook case for MSAA or
   supersampling. Tested both directly (8x MSAA; true 2x/4x pixel-density supersampling via
   render-resolution scaling), with every other mitigation disabled to isolate the effect:
   **neither changed the banding at all.** The visible artifact is large, coherent,
   many-pixels-wide bands with sharp transitions between them — not small-scale noise that finer
   sampling would resolve. Whole contiguous runs of adjacent, near-degenerate tetrahedra are
   producing a consistent (but displaced) result across a wide screen region, then jumping to a
   different consistent-but-displaced result in the next region over.

5. **Jittering the mesh's own subdivision grid doesn't break it either.** We tested displacing
   interior grid vertices by up to 30% of a grid step (tapered to exactly zero at seams, so no
   cracks). Confirmed via pixel-diff that this genuinely changes ~40% of the rendered output, yet
   the coherent banding survived essentially unchanged. This rules out "the artifact is just an
   accident of perfectly regular grid alignment" — moving vertex positions doesn't change which
   tetrahedra are topologically adjacent to which, and the instability tracks contiguous *bands*
   of near-degenerate cells, not exact grid coordinates.

**Bottom line**: every mitigation that operates per-fragment or per-sample (alpha fade, texture
blur, a shared-reference fallback, MSAA, supersampling) is structurally unable to fix this,
because none of them has access to what a neighboring, independently-computed tetrahedron
decided. The fix needs to change how the crossing-point formula itself behaves for genuinely
near-degenerate simplices.

## Proposed fix

**Bound `mix_weight`'s sensitivity by regularizing the denominator relative to the crossing
edge's own length — not relative to a fixed absolute value.**

Concretely, in `tetra_cross_section_shader.glsl` (and the equivalent in any custom shader that
reimplements this, e.g. `clouds.gdshader`):

```glsl
float w1 = position1.w;
float w2 = position2.w;
float raw_diff = w1 - w2;

// New: regularize the denominator's magnitude relative to the edge's own
// physical length, not a fixed absolute constant - this keeps the fix
// scale-independent (a tiny detailed mesh and a huge terrain brick both
// get an appropriately-scaled epsilon) without per-object tuning.
float edge_length = length(local_vert1 - local_vert2); // or view-space verts1/2, see below
float min_denominator = edge_length * RELATIVE_EPSILON; // RELATIVE_EPSILON e.g. 0.02-0.05
float safe_diff = (abs(raw_diff) < min_denominator)
    ? min_denominator * sign(raw_diff)
    : raw_diff;

float mix_weight = w1 / safe_diff;
vec4 position = mix(position1, position2, mix_weight);
```

This is the same `sensitivity = edge_length / |w1-w2|` quantity already derived and validated
this session as a genuinely scale-aware, well-behaved metric (a headless numeric sweep confirmed
it separates known-clean rotations from known-banded ones far better than the raw gap alone) —
here it's used directly as a **clamp on the geometry computation itself**, not as a trigger for a
separate fade/blur response.

**Why this should work, given everything confirmed above:**
- It directly targets the *proven* root cause (`mix_weight`'s unbounded sensitivity as
  `(w1-w2)→0`), not a downstream symptom.
- It bounds `d(mix_weight)/dw` to at most `~1/RELATIVE_EPSILON`, which bounds how much two
  geometrically-close-but-distinct tetrahedra's independently-exact crossing computations can
  diverge from each other — this is what actually produces the visible jump between adjacent
  screen regions.
- It changes the true output geometry (not just a texture-sampling coordinate or an alpha
  value), directly addressing the confirmed fact that the geometry itself carries the
  instability — unlike every previous mitigation, which only ever touched a downstream
  consequence.
- It does **not** reduce opacity or shrink/collapse any geometry. The output triangle stays
  fully present and fully opaque; only its exact position is bounded near the crossing
  threshold. No coverage gaps, no holes — this was the explicit failure mode of every earlier
  attempt and this fix doesn't have that shape of problem at all.
- It's a no-op (`safe_diff == raw_diff`) for the overwhelming majority of tetrahedra, at any
  ordinary viewing angle, since `RELATIVE_EPSILON` only matters when the true gap is already
  smaller than a few percent of the edge's own length.

**Known, honest trade-off**: for a tetrahedron whose true gap shrinks *past* the regularization
threshold, `mix_weight` stops tracking the further shrinkage and effectively "holds" at
approximately its value when the clamp engaged, rather than continuing to swing. As the object
rotates through the most extreme angles, the affected geometry may show a small, bounded lag
relative to a perfectly-instantaneous crossing, instead of the current large, sharp jump. This is
expected to be far less visually objectionable than the current banding (bounded and smooth vs.
unbounded and sharp), but it is a real, deliberate trade-off, not a fully "exact" fix — consistent
with the fact that the underlying formula is genuinely, provably ill-conditioned in this regime
and *something* has to give.

## Testing plan results — DO NOT SHIP AS IMPLEMENTED

The testing plan below was executed in full: the engine was actually rebuilt with this fix, the
fixed rotation set was actually rendered fix-on vs fix-off with every existing mitigation
disabled, `RELATIVE_EPSILON` was actually swept across 6 values via renders (not just the numeric
metric), and terrain was actually spot-checked. Every claim below is backed by a same-crop,
explicitly-labeled, directly-viewed image, saved under `project/_verify_screenshots/` — none of it
is inferred from the metric alone or from a full-frame glance. **The honest result: the "known
trade-off" described above (a small, bounded, smooth lag) is not what actually happens. Instead,
this specific implementation introduces a new, real, visually severe artifact that isn't present
in current behavior, at every tested `RELATIVE_EPSILON` value, with no clear improvement to the
original banding to offset it.** This fix should not ship in its current form.

**Steps 1-3 (build, render the fixed rotation set, confirm clean angles unchanged) — passed.**
The engine rebuilt in ~80 seconds (only the changed `.glsl.gen.h` and its dependents recompiled).
At 0°, 20°, and 45° — `relepsilon_0deg_composite.png`, `relepsilon_20deg_composite.png`,
`relepsilon_45deg_composite.png` — fix-on and fix-off are visually indistinguishable, exactly as
predicted for a regularization that's a no-op away from near-degenerate crossings.

**Step 4 (confirm 80°/88° improve) — failed.** At 80° (`relepsilon_80deg_composite.png`) the two
configurations again look effectively the same — no meaningful reduction in the existing banding.
At 88° (`relepsilon_88deg_composite.png`, and zoomed further in `relepsilon_88deg_anomaly_composite.png`)
fix-on does **not** show reduced banding severity either — but it does show something new: a
sharp, jagged, sawtooth-shaped notch cut into the cloud silhouette, running most of the length of
the visible slab, that is **completely absent** from fix-off (current behavior). This is not a
softened version of the existing artifact; it's a distinct, additional visual defect.

**Step 5 (sweep `RELATIVE_EPSILON` if 0.03 over/under-corrects) — done, confirms the defect isn't
a tuning accident.** Swept 0.01, 0.02, 0.05, 0.08, 0.12, 0.2 at both 45° (control) and 88° (problem
case), rendered, not just computed. `relepssweep_88deg_composite.png` (four of the six values,
same tight crop, labeled) shows the notch **monotonically growing with `RELATIVE_EPSILON`** — from
barely perceptible at 0.01, to the same clearly-visible cut already seen at the proposed default
0.03, to a large, severe wedge at 0.2. At no tested value does the notch disappear, and at no
tested value is there visible improvement to the pre-existing banding to weigh against it. At 45°,
values at/below the proposed 0.02-0.05 range stay clean, but 0.2 (`relepssweep_45deg_eps0_2_full.png`)
shows the *same kind* of small triangular notches appearing at a previously-always-clean rotation —
confirming this is a general property of the mechanism, not an 88°-specific fluke.

**Root cause of the new defect (why the "smooth lag" reasoning above was wrong):** `regularized_diff`
is a continuous function of its own input for one single edge — as that edge's own `raw_diff`
shrinks toward zero and past the clamp threshold, the returned value doesn't jump. But the visible
artifact is a comparison between **two different, adjacent tetrahedra**, each with its own edge,
its own `edge_length`, and its own independently-evaluated threshold (`edge_length * RELATIVE_EPSILON`).
Nothing keeps two geometrically different neighbors from landing on opposite sides of *their own*
threshold at the same moment — one tetrahedron's crossing edge can be clamped while its immediate
neighbor's isn't, and the two independently-exact results can disagree sharply right at their
shared boundary. That's structurally the same "neighboring, independently-computed simplices
disagree" mechanism that causes the *original* banding bug — this fix relocates that mechanism
from the true `w=0` crossing to the clamp's own engagement boundary, rather than eliminating it.

**Step 6 (spot-check terrain for regressions) — passed, with a scope caveat.** Terrain (a real
generated island via `VoxelTerrain4D`, the engine's own default cross-section shader, not
`clouds.gdshader`'s copy) was rendered fix-on vs fix-off at 0°, 30°, and 60°
(`relepsilon_terrain_0deg_*`, `_30deg_*`, `_60deg_*`) — all three pairs are visually identical, no
regression at any of these. **Caveat**: none of these rotations pushed terrain into a genuinely
near-degenerate crossing the way the clouds box's huge W-extent does at 88° — terrain's own
geometry may or may not be able to reach that regime under ordinary play, and this spot-check
did not attempt to force it. This confirms "no regression at ordinary angles," not "the fix is
safe at terrain's own worst case," which remains untested.

**Recommendation**: do not ship this `RELATIVE_EPSILON` clamp as implemented — it fails to reduce
the banding it targets and adds a new, worse-looking defect at the exact rotation it was meant to
fix. Two honest directions forward, neither attempted here: (a) replace the hard clamp with a
continuous blend (e.g. `smoothstep` the denominator toward the clamped value over a small range
approaching the threshold, so two neighbors near their respective thresholds converge toward each
other instead of snapping independently) and re-run this same rendered-comparison methodology
against it; or (b) accept that this specific geometric approach doesn't pan out and continue
relying on the already-shipped mitigations (`degeneracy_threshold`-triggered blur), which are a
real, measured, partial improvement with no equivalent regression, per
`CLOUDS_BANDING_TECHNICAL_SUMMARY.md`.

## Separate, unrelated hygiene item (no engine rebuild, low risk, does NOT address the banding): fix the noise atlas's own mip chain

Independent finding from the isolation test above, **kept only as unrelated hygiene, not as a
companion fix for the banding** (see the corrected update at the top of this document — a direct,
labeled side-by-side comparison showed proper texture filtering does not meaningfully reduce this
specific artifact): the project's clouds noise is stored as a hand-packed atlas — 48 seamless
tiles (one per depth "slice" of a pseudo-3D noise volume) packed into a single 2D image, sampled
via manual tile-origin arithmetic in `clouds.gdshader`. Godot's default mipmap generator
downsamples that whole packed image uniformly, with no awareness that it's 48 independent tiles —
every mip level above 0 already permanently blends unrelated neighboring tiles across their shared
boundaries. The existing workaround is forcing `textureLod(..., 0.0)` everywhere (see
`sample_slice()` in `clouds.gdshader`), which avoids the corruption but also means **there is no
anti-aliasing at all** for this texture, at any minification level, mild or severe — a real,
if lower-stakes, problem on its own (e.g. clouds viewed from far away, at ordinary, non-degenerate
rotations, still get no mip filtering today).

**Recommended fix (independent of the banding fix above)**: replace the manual atlas-of-2D-tiles
trick with a real `Texture2DArray` (48 layers, one per depth slice), sampled via
`sampler2DArray`/`texture(sampler, vec3(uv, layer))` in the shader. Godot generates and filters
mipmaps correctly per-array-layer with no cross-layer bleeding — a native, well-supported GPU
texture type built exactly for this "many independent 2D slices" use case, removing the need for
the atlas's manual tile-origin arithmetic and the forced-LOD-0 workaround entirely. This is a
**project-side, no-engine-rebuild change** (a different Godot resource type plus a shader rewrite
of the sampling functions, no C++), lower risk than the geometric fix above, and worth doing on its
own merits — but **do not expect it to help the grazing-angle banding**; that requires the
geometric fix above.

## Scope and containment

- **Files touched**: `engine/modules/4d/render/cross_section/tetra_cross_section_shader.glsl`
  (the engine's own default shader — fixing it here benefits every 4D object project-wide, not
  just clouds), and `project/scripts/clouds.gdshader` (our custom material's copy of the same
  logic, kept in sync per the existing convention). Also worth checking
  `engine/modules/4d/render/cross_section/wireframe_cross_section_shader.glsl` for the same
  pattern, if it independently reimplements crossing-point computation.
- **Size of change**: a handful of lines replacing one existing formula with a regularized
  version, in an already-isolated, well-understood function. No changes to the tetrahedron data
  structures, the `CROSS_SECTION_LOOKUP` table, mesh construction, or any other file.
- **Rebuild required**: yes — this file compiles into the engine binary
  (`tetra_cross_section_shader.glsl.gen.h` is a generated header), so this requires an engine
  rebuild, not just a runtime shader/script reload. It does **not** require touching C++ code.
- **Blast radius**: this shader is shared by every 4D object using Cross-Section rendering,
  including the terrain — but the change is designed to be a no-op away from genuinely
  near-degenerate crossings, so the expected regression risk elsewhere is low. This should still
  be verified directly (see testing plan) rather than assumed.

## Open question for review

`RELATIVE_EPSILON`'s right value is a real design choice, not yet empirically tuned — it trades
"how much lag is acceptable in the most extreme case" against "how tightly does this bound the
worst-case jump." Proposing to start around 0.02-0.05 (2-5% of a crossing edge's own length) and
calibrate against rendered before/after crops at the same problem rotations already established
in this investigation (a 45° control that must stay pixel-identical to today's behavior, and an
80-88° range that should show the banding meaningfully reduced), the same methodology used
throughout this investigation.

## Testing plan (before considering this done)

1. Build the engine with the change, `RELATIVE_EPSILON` at an initial guess.
2. Render the same fixed rotation set already used throughout this investigation (0°, 20°, 45°,
   80°, 88°) with every existing shader-side mitigation (alpha/blur/cell-center) **disabled**, to
   see this fix's effect in isolation.
3. Confirm 0°/20°/45° are pixel-identical (or imperceptibly close) to current behavior — this
   fix must not visibly change anything away from genuinely near-degenerate crossings.
4. Confirm 80°/88° show the banding meaningfully reduced or eliminated, via the same crop-level
   before/after comparison methodology already used (not just numeric proxies).
5. Sweep `RELATIVE_EPSILON` if the first guess over- or under-corrects, using the same render-based
   calibration approach (not just the numeric metric alone — confirmed multiple times this
   session that a metric's numeric behavior and its rendered visual severity aren't always what
   naive intuition predicts).
6. Spot-check the terrain (a different consumer of the same engine shader) at a few rotations to
   confirm no unexpected regression, given the shared blast radius.
